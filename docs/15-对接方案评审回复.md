## 二、三个主决策：全部接受，附实施条件

### 决策 1（文档级推送）：✅ 接受，作为主协议

- 同意贵方理由：检索质量优先（Summary chunk/语义切块/Wiki 三项能力必须保留）；溯源字段（filename / chunk_index / start_at·end_at / knowledge_id + 文档回查）**强于** caller 侧自造 chunk.id；按 doc_id 幂等语义更干净。
- **实施条件（我方内部）**：14 号契约是通用契约，我方 Embedded 参考实现必须实现**同一文档级语义**（内嵌切块器）——"参考实现即规格"原则不能破。已排入 v0.4-a（增量约 0.5~1 人日）。
- chunk 级保留为**降级模式**（规格附录）：语义按贵方 §二.决策1.5——该模式损失 Summary/Wiki/语义切块三项，检索质量预期书面调低。
- 溯源五字段 + `GET /knowledge/document/{id}` 回查链路，写入规格 v1.2 必填项。

### 决策 2（Scoped API Key + 请求体去 project_id）：✅ 接受

- 我方 Embedded 模式（进程内、无 HTTP）不受影响：project 上下文在 `KnowledgeGateway` 抽象内部管理，契约仅在 HTTP 边界生效。
- 越权语义 `40301` ↔ `scope_denied` 按本文 §四映射表处理。

### 决策 3（走法 A：KbOsGateway 薄适配器）：✅ 接受

## 四、错误码：采用**字符串码**（我方定版立场）

**理由**：可读性（代码分支、日志、grep、对拍失败信息全部自描述）；数字码对消费方是持续的查表负担，且排障时不可读。行业语义惯例（gRPC/主流 HTTP API）亦以字符串语义码为主。

**落地两步（不互相阻塞）**：

1. **短期（W1 即可开工）**：走法 A 下由 `KbOsGateway` 适配器内做数字→字符串映射（映射表如下，写死在适配器与契约测试断言中）；
2. **建议（P1 增强）**：贵方 Envelope 增加可选字符串字段 `error_key`（向后兼容——新增字段不破坏），启用后适配器直读、映射表退役。

**映射表（kb-os 数字码 ↔ 规格 v1.2 字符串码）**：

| kb-os code | 规格字符串码 | 备注 |
| --- | --- | --- |
| 0 | （成功） | — |
| 40001 | `invalid_request` | 参数非法 |
| 40101 | `unauthorized` | 凭据无效/缺失 |
| 40301 | `scope_denied` | 越权/跨项目 |
| 40401 | `not_found` | ⚠️ 口径待 W0 确认：v1.2 拟将 404 码泛化为 `not_found`（覆盖库/文档/条目，资源类型入 message），替换 v1.1 的 `entry_not_found`（pre-GA 修订） |

## 五、就绪信号：定版建议为**文档级 `parsing`**

我方 v1.1 用的是 chunk 级 `pending_parse`；经评估，**文档级更优**，v1.2 将改口径（pre-GA 正常修订）。理由：

1. **单元一致性**：主协议下入库/幂等/重试的单元都是文档，就绪观测单元也应是文档——否则"重试按文档、观测按 chunk"错位；
2. **chunk 级对消费方是"没有分母的进度条"**：我方不再切块后，单篇文档产出多少 chunk 是贵方内政（语义切块/Summary chunk 均内部决定），`pending_parse: N` 我方既算不出进度、也分不清"在跑"与"卡死"。文档级则有强不变量：**`documents + parsing` = 累计已接受文档数**，联调一眼可查；
3. **不泄漏内政**：决策 1 的精神是切块主权归知识库；契约可见的 chunk 计数会把内部切块策略暴露成契约状态。

**契约定义（v1.2）**：`parsing` = 已接受、尚未完成索引的**入库单元**数——主协议单元=文档；chunk 降级模式单元=chunk（字段名不变，**就绪判据 `parsing == 0` 在两种模式下均成立**）。同步实现（Embedded 同步直写）恒为 0，同样合规。

**可选扩展建议**：stats 增加可选字段 `parse_failed`（解析失败数，可重推）——联调排障与"静默丢文档"检测用，向后兼容。
