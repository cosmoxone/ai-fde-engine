# 开源商业双轨与 EE 目录规划

> 版本：**v1.0** | 日期：2026-09-18 | 基于：v0.4.0 已发布；[10-商业计划](10-商业计划.md) Open-Core 模式
> 产物：`ee/` 目录骨架（README / 商业许可占位 / roadmap-ee）——本文是其设计依据与双轨总纲
> 一句话：**CE 用契约化扩展点保持"可独立运营的开源内核"，TE/EE 在 ee/ 内做"只加不减"的商业增量**

---

## 1. 为什么现在建 ee/（触发与时机）

v0.4.0 完成了两个关键架构动作，使双轨在工程上变得**低成本**：

1. **契约化外部模块**：知识库（14 号）/本体（20 号）已从内核解耦为 Gateway+契约面——
   TE 的"团队共享 KB"、EE 的"租户级 KB 策略"都能通过契约面编排实现，**不动内核**；
2. **参考实现即规格**：Embedded 行为基准 + 契约测试套件，商业版替换实现时有现成验收标准。

即：**CE 的扩展点已经契约化，ee/ 只是把这些扩展点的商业实现收拢到独立许可空间**。

## 2. 双轨总纲

```
┌─────────────────────────────────────────────────────────┐
│  CE（MIT，仓库主体 src/）                                 │
│  单机·单用户·全核心功能免费                                │
│  扩展点 = 契约 14 号/20 号 + Gateway 抽象 + webhook 集成    │
└───────────────┬─────────────────────────────────────────┘
                │ 单向依赖（ee → CE，反向禁止）
┌───────────────▼─────────────────────────────────────────┐
│  ee/（商业许可，LICENSE-COMMERCIAL）                      │
│  TE v1.0：多用户协作·团队共享 KB·团队经验库（订阅）          │
│  EE v1.x：多租户 SaaS·白标·SSO/RBAC·审计合规（一口价）       │
└─────────────────────────────────────────────────────────┘
```

**四条工程红线**（详见 ee/docs/roadmap-ee.md）：
1. 单向依赖（CE 不 import ee；开源 CI 不构建 ee）
2. 契约即扩展点（不 fork 内核网关）
3. 只加不减（EE 不阉割 CE 能力）
4. 开源回馈（通用修复合回主线）

## 3. 版本规划（与 CE roadmap 的咬合）

| 时间线 | CE（开源主线） | ee/（商业轨） |
| --- | --- | --- |
| v0.4.0 ✅ | 知识与本体（契约×对拍×RAG 终验） | —（架构就绪：契约面成型） |
| v0.5 | 生态联动实测（night-factory 真跑/RPA 对拍）、黄金集扩展、稳定性 | **TE v1.0 首交付**：多用户认证 + 团队共享 KB（kb-os key 池编排）+ 团队经验库 |
| v0.6+ | 性能验收、PyPI、模板生态 | EE v1.0：多租户存储层 + SSO/RBAC + 白标 + 审计包 + K8s SaaS |
| 持续 | 契约 P2 演进（entity 过滤/批量 confirm/webhook） | EE 同步跟进（契约升级窗口=EE 验证窗口） |

**节奏原则**：CE tag = EE 构建基线；契约面稳定时 EE 升级成本≈重跑测试矩阵。

## 4. ee/ 目录结构（已落地骨架）

见 [ee/README.md](../ee/README.md)：README（定位/许可/构建关系）· LICENSE-COMMERCIAL（占位条款）
· docs/roadmap-ee.md（功能分级总表 + 交付顺序）· src/{multi_tenant,auth,branding,collaboration}/（占位）
· deploy/（EE 镜像 = FROM core + ee 层）· tests/（独立 CI）。

## 5. 商业化第一个交付的最小路径（TE v1.0 MVP）

1. `ee/src/auth/`：邮箱密码 + 邀请制（FastAPI 依赖注入，CE 无感知）
2. 项目成员表 + 任务分派（StorageProvider 扩展接口，SQLite/PG 双实现）
3. 团队共享 KB：**纯编排**——kb-os 多项目 scoped key 池 + CE 既有 Fallback 网关（零内核改动，~2 人周）
4. 团队经验库：CE 记忆层加"团队共享域"标记
5. 计量：席位/用量埋点（为订阅计费供数）

## 6. 开源侧的配套承诺（对社区）

- CE 功能永不全量商业化（"只加不减"红线写进 ee/README 与本文）
- 契约文档（14/20 号）永久开源——第三方可自实现替代 kb-os/本体服务（这正是 Open-Core 的信任基础）
- 商业版产生的通用修复 100% 回馈主线（CHANGELOG 标注来源）
