## 2. 差距分析（演示形态 → 平台租户形态）

| # | 差距 | 影响 |
| --- | --- | --- |
| G1 | 鉴权为全局静态 token | 多租户下无法按 org 隔离——TE 无法开放本体共享域 |
| G2 | X-Onto-Project 无租户约束 | 任意持有 token 方可写任意 project（含他人域） |
| G3 | 无 tenant 维度审计 | 平台事件 schema（platform.audit.v1）要求 tenant_id 一等 |
| G4 | 无配额/限流租户桶 | 与 kb-os 24 号 40302 治理面不对齐 |

## 3. TE 需求清单（R1-R5，按优先级）

### R1【必须】凭证：接入平台 keystore（不自建 key 体系）

按平台规范 §2.2，**机器凭证全平台统一走 kb-os keystore**——本体服务验证 kb-os 签发的
scoped key（`kbos-{name}-{24hex}`、服务端 sha256 比对、scopes 词表 read/write/admin），而非
自建发放面。预期契约=24 号 §3 同构（key 即 principal；scopes 子集律服务端不涉及——只验不发）。
备选：W17b JWT 轨（audience=ontology）——若本体服务已接 CASDoor JWKS 可二选一，**推荐前者**
（机器凭证面统一，零新增）。

### R2【必须】项目上下文租户化（命名域同构 kb-os）

`X-Onto-Project` 值域约束为 `{org}`（项目私域）与 `{org}-shared`（租户共享域）——与 kb-os
`te-{org}-p{N}` / `te-{org}-shared` **命名域同构**（前缀策略本体服务自定，语义对齐规范 §3：
key 归属租户外越域 → 40401 存在性隐藏 / 显式越域 40301）。

### R3【确认】共享域 merge 语义

既有幂等 merge（实体属性合并/图不重复增长/软删不复活）**直接适配**共享域——TE 侧"项目本体
合并入团队域"= 以 shared project 上下文调 `/extract`。请本体服务确认无额外改动。

### R4【应该】审计：按 platform.audit.v1 发射

`source_service=ontology`（进程级稳定名），tenant_id 取自 key 归属（R1 验证结果），
动作沿契约 20 端点（extract/graph/delete_entity…）。schema 见 kb-os `platform/docs/平台事件schema.md`。

### R5【可选·P2】配额租户桶（40302 语义对齐 kb-os）

按需；首版可缓（本体写入量级低）。

## 4. CE/TE 消费侧改造点（本方自行完成，工作量小）

1. `ee/src/saas/onto_runtime.py`（类比 kb_runtime）：per-org 网关工厂——`X-Onto-Project`
   注入 `{org}`/`{org}-shared` + per-tenant key（R1 落地后从 kb_pool 同源取）；
2. 单 token 兼容：local 直跑档沿用 `ONTOLOGY_SERVICE_TOKEN`（单 org 语义，类比知识库 embedded 模式）；
3. 共享域发布流（merge 入 shared）挂 M3 shared_kb 同款权限/审计面。

schema——本体服务租户化是"接入平台"而非"再造平台"。**
