## 二、§5 ①②③ 正式答复

### ① 租户命名空间映射：✅ 确认，且与我方既有设计零改动对齐

- **TE 命名空间 = `te`，下游租户 = `te-{org_id}`**——即 kb-os 侧 `tenant_id = te-{org_id}`。
- 依据：TE 设计已定 kb-os 项目命名域 `te-{org}-shared`（团队共享）/
  `te-{org}-p{N}`（项目私域）（design-te-v1 §3/§4.1）。kb-os key 租户号与项目名
  **同前缀**，key name = 项目名即可完成"租户→项目→key"对账闭环，无需额外映射表。
- org_id 语义：TE 侧租户 = Org（订阅主体，CASDoor Org 映射，PG 行级 scope）。
  **org_id 取短 slug**（3~12 位字母数字，租户注册时生成/自定义，TE 内全局唯一）；
  不用 UUID 全长（key 名可读性与长度）。`te-` 前缀保证 kb-os 侧命名空间自洽。

### ② 配额与池划分

| 项 | 答复 |
| --- | --- |
| 每租户默认 100 | ✅ 够用。每 Org 活跃 key = 1（shared）+ 项目数 N + 少量备用；Lite 档个位数项目、Pro 档几十项目量级，100 留足余量。EE 大租户将来单独提额（可配置即满足） |
| 池划分（default/eval） | **TE M3 只用 default 单池**；eval 池不启用，M3 后视计量/风控需要再议 |
| labels 列 | **确认不需要，按贵方精益注裁掉**——tenant_id + pool + key name（=项目名）已覆盖 TE 对账面 |
| 命名空间总配额 `KBGW_NS_KEY_QUOTA` | **建议启用**（选配转正）——"泄漏一把 tenant-admin 可在 N 个下游租户各发配额内 key"正是我方最关心的残余攻击面；初值建议 **500**（初期租户数 <10），可配置即可 |

### ③ TE M3 最早时间点

- TE M1（Casdoor/org 贯通）1.5 周 + M2（协作）2 周 → **M3 约 10 月中旬进入开发**；
  首个真实租户上线（内测）在 M3 完成之后（~11 月初）。

  真实租户接入前就位**（越权面 G1 不能带病上线）。

## 三、两个澄清问题（不阻塞 M0，请随 M1 实现一并答复）

1. **tenant-admin 委派 key 自身的 scopes 集合未写明**——它是子集律的"天花板"，需定版。
   我方拆分建议：
   - 租户委派链：tenant-admin 自身 scopes = `kb:read`+`kb:write` → 下游项目 key 全部
     read/write（检索/入库/重推发布，M3 共享发布流走幂等 ingest，不需要 admin）；
   - `kb:admin`（契约 14 P1 curate confirm/reject）由 **TE 平台侧持独立服务 key**
     执行（平台方直接签发，不经租户委派链）。
   请确认此拆分（或告知贵方倾向的替代方案）。
2. **M0→M1 存量 key 纳管策略**：TE 若即日起按 M0 + 命名约定发 key，M1 表迁移后这些
   key 的 `tenant_id=''`（未纳管），tenant-admin 管辖域（ns 及 ns-%）看不到也管不了。
   两种处置请贵方选定并告知：**(a)** 贵方提供按 name 前缀回填 tenant_id 的纳管工具；
   **(b)** 我方 M1 就绪后全量重发（项目 key 轮换，~30s 缓存延迟窗口我方可接受）。
   若 (b)，请确认重发期新旧 key 并存的限流/审计口径。
