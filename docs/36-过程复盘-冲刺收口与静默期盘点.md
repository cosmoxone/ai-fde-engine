## 5. 经验教训

1. **"复盘落档"≠"状态收口"**：34/35 号复盘写得很全，但仓库状态没有同步——纸面闭环掩盖了
   版本控制敞口。**冲刺结束仪式必须是"复盘落档 + 提交 + 推送"三件套**，缺一不可。
2. **双轨拆分的完整动作是"移出+移入"**：ee/ gitignore 决策本身正确（开源仓不含商业码），
   但"移出开源仓"只是半步，"移入私仓"才是完整闭环。半步决策制造了比原来更大的单点风险。
3. **静默期是风险放大器不是风险免疫期**：不写代码 ≠ 安全。21 天里若发生磁盘故障/误删，
   损失与"高强度开发期"完全相同，且无人察觉。**长静默前应做"落库快照"**（哪怕 WIP 提交）。
4. **测试基线的自我价值**：静默 21 天后一次 `pytest` 即证明零回归（637 绿）——固定 canonical
   顺序 + 全 mock 默认 + 90s 可跑完的基线，让"恢复工作"的第一步成本几乎为零。**这是留给自己
   未来的最好礼物**（34 号纪律"全量回归固定顺序"的直接回报）。
5. **文档数字要单一源**：测试数/版本号在 README、docs/00、health 三处手工维护必然漂移。
   能代码化的（health version）读单一源；不能代码化的标注"截至 vX 日期"限定语。
6. **运行态与代码态分离要落到 ignore 清单**：envs/ 体系解决了"怎么跑"，没解决"跑出来的东西
   放哪不碍事"——DATA_PREFIX 设计了，.gitignore 没跟上。**每次新增运行产物目录，同一 PR 内
   补 ignore**（34 号"文档迁移配引用扫描"的同款纪律）。
