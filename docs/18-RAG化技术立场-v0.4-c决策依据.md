# RAG 化技术立场：v0.4-c 决策依据

> 版本：**v1.0** | 日期：2026-09-17 | 状态：**已定稿**（技术立场记录，等待 kb-os 联调期间讨论沉淀）
> 关联：[13-本体与知识库深化设计](13-本体与知识库深化设计.md) §3.3 机制 2 / [09-后续规划](09-后续规划.md) v0.4-c / [14-知识库接口规格](14-知识库接口规格.md) v1.2
> 触发问题：*"之后有一个 RAG 化，是啥意思，为啥？现在不是都追求 RAG-less 么，用 wiki LLM 这种，RAG 的使用范围小了很多啊"*

---

## 1. 结论先行

**RAG-less 趋势淘汰的是"无脑向量检索管线"，不是"检索"这个动作本身。** 本项目的"RAG 化"= 把 research 模块现状的**静默截断**换成**带出处的按需检索**；实现路径（FTS5+BM25 词法检索 + 人工审校 + 溯源必填 + 黄金集回归门槛）恰好是这波批评之后该有的形态。且 v0.4-c 以**实验**而非信仰推进：黄金集倒退即回退全文模式。

## 2. 我们的"RAG 化"是什么：先修截断，不是上向量库

v0.4-c 之前 `src/agents/research.py` 的真实输入路径：

```python
# _aggregate_inputs()：单文档截断
parts.append(f"=== {title} ===\n{content[:8000]}\n")
# _perform_analysis()：总输入再截断
{content[:30000]}
```

客户传 10 份文档、每份 5 万字，**约 97% 内容被静默丢弃**，后续"业务流程还原"在残卷上进行。

v0.4-c（13 号 §3.3 机制 2）：`_perform_analysis` 输入改为 **Gateway 检索 top-k 相关块（带出处）+ 本体压缩摘要**，替代全文塞入。解决的是截断与成本，不是"要不要 embedding"。

## 3. RAG-less 趋势批评的靶心，与我们无交集

当前 RAG-less 路线（长上下文全塞 / 微调蒸馏 / agentic grep 搜索）打击的是 **embedding 向量管线**（切块→向量化→余弦召回→塞 top-k）的脆弱性：召回错一块整段废、切块算法玄学、语义漂移。

本项目**不含这条管线**：

| 趋势批评的弱点 | 本项目现状 |
| --- | --- |
| embedding 召回脆弱 | Embedded 实现为 **FTS5 + BM25 词法检索** + 标题感知切块，零 embedding（短查询 LIKE 兜底） |
| 检索质量不可控 | **curated 人工审校队列**：人确认的 FAQ 加权 ×1.05 先出；LTR 反馈学习 |
| 算法绑定供应商 | 契约不绑定检索算法；kb-os 侧语义切块/Summary/Wiki 均为可选增强；Gateway 抽象可换实现 |
| 单轮召回一锤子买卖 | Gateway API 天然支持 **agentic 多轮检索**（agent 改写 query 多次调 search），无需改契约 |

## 4. 场景分析：为什么"检索"动作在本场景缩不掉

RAG-less 的适用前提：知识**静态、公共**（预训练可见）、或**语料小到塞得下**。本项目一条不占：

| 本项目特点 | RAG-less 方案的死穴 |
| --- | --- |
| 知识**项目私有**、运行时上传 | 每项目微调一版？成本/时效/数据主权均不通（契约 scoped key 即按项目隔离） |
| 知识**时变、可吊销**（pending→confirm/reject 生命周期） | 模型权重静态，删一条 curated 条目模型仍"记得" |
| **溯源是硬需求**（14 号契约溯源五字段必填） | 参数化记忆给不了出处只会幻觉；FDE 交付结论必须能指出"哪份文档哪一节说的" |
| 几十份文档超上下文预算 | 全文塞入 = 成本 ×N + lost-in-the-middle；现状截断更糟（见 §2） |

## 5. "wiki LLM"辨析

- **路径 A（知识蒸馏进模型权重）**：适用于**静态公共知识**——FDE 通用方法论、行业通识。本项目这部分走 system prompt / 行为设计，**本来就不该检索**，与 RAG 化不冲突。
- **路径 B（LLM 像 Agent 一样浏览知识库）**：本质**仍是检索**，只是 agentic 化（自主改写 query、多轮 search、按需深挖）。Gateway API 完全支持此形态；若 v0.4-c 之后 research agent 升级为 agentic 检索，契约与实现均无需变更。

## 6. 实验框架：数据说话，不是信仰

v0.4-c 的验收与退路（13 号 §五 实施排期）：

- **验收门槛**：黄金集 ≥100% 不倒退（不倒退才能转正）+ RAG vs 全文 token 成本对比数据（发布时 golden-real 报告出两栏）
- **降级预案**：分步灰度——先"RAG + 全文摘要"混合，回归通过再纯 RAG；倒退则**保留全文模式为默认**

**适用边界规则**（随 v0.4-c 实施落地）：

1. 静态领域通用知识 → system prompt，不进知识库、不检索；
2. 单项目语料极小（数千 token 内）→ 直接全文注入，跳过检索；
3. 超出上下文预算的项目私有语料 → Gateway 检索注入（RAG 化的目标场景）。

## 7. 结论

RAG 的适用范围确实在收缩——收缩掉的是"静态公共知识"与"小语料"场景。本项目场景（**项目私有 + 运行时时变 + 溯源硬需求 + 超上下文预算**）恰是缩不掉的剩余部分；而实现上（词法检索、人工审校、溯源必填、回归门槛、可退全文）已规避向量管线全部已知弱点。RAG 化在此是**带止损线的实验**，而非技术站队。
