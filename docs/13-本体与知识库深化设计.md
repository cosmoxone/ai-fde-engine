# 卖点 1+2 深化设计：本体抽取 × 知识库独立模块

> 版本：设计稿 v1.0（2026-09-08）｜ 目标版本：v0.4.0 ｜ 状态：待评审
> 范围：卖点 1（本体抽取→业务建模→需求分析）与卖点 2（自动知识库+自动化 Benchmark）的实现深化与双向整合
> 原则：单机零依赖优先（CE 默认可跑）、验证前置（黄金集不倒退）、Mock-first（LLM/向量可选增强）

---

## 一、现状与差距（对照代码实况）

### 卖点 1：本体抽取与需求分析

| 环节 | 现状（v0.3.0） | 卖点主张 | 差距 |
| --- | --- | --- | --- |
| 文档输入 | DocParser 解析为纯文本 + structured 段落 | 客户数据 + **主动调研** | 主动调研缺位 |
| 抽取 | research 时 LLM 一次性输出 JSON（business_process 文本列表） | **本体抽取**（实体/关系/规则的结构化沉淀） | 输出是"描述文本"不是"可查询本体"，不可复用 |
| 建模 | requirements_baseline 里的业务流程为一次性生成 | 业务建模（本体图驱动） | 无图结构、无增量、每次全量重跑 |
| 需求分析 | 全部文档塞 prompt（M2.7 实测 100% 要点命中，单文档场景优秀） | 大文档量也稳定 | **文档多时超 context / 成本爆炸**，无检索增强 |

### 卖点 2：自动知识库 + 自动化 Benchmark

| 环节 | 现状 | 卖点主张 | 差距 |
| --- | --- | --- | --- |
| 知识库 | `tools/knowledge_base.py` 存在但**不在主流程**（孤岛：无任何端点触发建库） | 自动搭建知识库 | 文档上传后不会自动入库 |
| 后端 | qdrant 或 mock 二选一 | 开箱即用 | 缺**零依赖本地后端**（SQLite FTS5 即可，中文 trigram 分词可用） |
| Benchmark | 直接从文档原文生成 | 自动化 Benchmark | 不经知识库检索，**用例无出处溯源** |
| 迭代闭环 | badcase 修复建议是文本草稿 | 闭环沉淀 | "知识缺失"类 badcase 未回写知识库（建议→确认→入库缺失） |

**结论：两个卖点的核心差距交汇于同一缺失——「知识库独立模块」既没建成，也没把卖点 1/2 串起来。**

## 二、目标架构

```
客户文档（上传/API/批量导入）
        │
        ▼
   DocParser（解析）
        │
        ├─────────────① 本体抽取管线（卖点1）──────────────┐
        │   LLM 结构化抽取：实体/关系/业务规则               │
        │   增量 merge（新文档只抽新知识）                   │
        │              ▼                                    │
        │      OntologyStore（SQLite，项目级本体图）          │
        │       entities / relations / rules                 │
        │              │ schema 层（结构化知识）              │
        ├─────────────② 知识索引管线（卖点2）────────────┐   │
        │   切块 → 检索索引（上传即自动建库）              │   │
        │              ▼                                  ▼   │
        │      KnowledgeService（独立模块，内容层+schema层联动）│
        │       LocalFts(SQLite FTS5) ←默认│ Qdrant ←可选增强 │
        │              │                                    │
        ▼              ▼                                    ▼
 ResearchAgent：检索增强（RAG top-k 替代全文）+ 本体图注入 → 需求基线（带出处）
 BenchmarkTool：从知识库检索生成用例（每条带 source 溯源）
 夜间迭代闭环：badcase(知识缺失) → KnowledgeEntry 草稿 → 人工确认 → add_curated 入库 → 下轮回归受益
```

**关键设计决策**：
1. **知识库为独立模块**（`src/knowledge/` 包，不再是 tools 下的工具类）——接口契约清晰，未来可独立部署为服务（TE 多用户共享库）
2. **双层知识模型**：schema 层（本体图：实体/关系/规则）+ 内容层（文档块检索）——这是卖点 1/2 整合的枢纽
3. **三级检索后端**：`LocalFts`（SQLite FTS5 trigram，零依赖默认）→ `Qdrant`（向量增强，可选）→ `ExternalAPI`（预留）——开箱即用与生产增强兼得
4. **Embedding 诚实降级**：无向量服务时不硬造"假向量"，用 FTS trigram + BM25 排序（中文实测可用）；配置 embedding API 后自动升级向量检索

## 三、模块设计

### 3.1 KnowledgeService（卖点 2 主体，`src/knowledge/`）

```python
# src/knowledge/service.py
class KnowledgeBackend(ABC):
    """检索后端契约：LocalFtsBackend（默认）/ QdrantBackend / ExternalAPIBackend"""

class KnowledgeService:
    """项目级知识库：内容层检索 + curated 条目 + 本体联动"""

    # 索引（上传文档后自动调用；亦可手动重建）
    def ingest_document(self, project_id: str, doc: dict) -> IngestReport
        # 切块（按段落/标题，300-500字块）→ 后端索引，保留 source(filename, para_idx)

    # 检索（混合：curated条目优先 → 后端 top-k → 可选本体过滤）
    def search(self, project_id: str, query: str, top_k=5, entity_type=None) -> list[KnowledgeHit]
        # KnowledgeHit: {content, source, score, entry_type: chunk|curated|ontology}

    # 人工确认知识条目（迭代闭环入口）
    def add_curated(self, project_id: str, entry: CuratedEntry) -> str
        # CuratedEntry: {question_pattern, answer, source_badcase_id, status: confirmed}

    def stats(self, project_id) -> dict   # 块数/curated数/覆盖率
```

**数据落点**：SQLite `data/aifde.db` 新增 `kb_chunks`（FTS5 虚表：content/source/project_id）与 `kb_curated` 表——与业务存储同库，备份/迁移一体。

**上传自动建库**：`upload_document` 与 `parse_batch` 后挂 `ingest_document` 钩子（失败不阻断上传，报告状态）。

### 3.2 OntologyStore（卖点 1 主体，`src/ontology/`）

```python
# src/ontology/store.py
@dataclass
class Entity:   id, type(物料/检验单/角色/系统/流程节点...), name, properties: dict, source_doc
@dataclass
class Relation: from_entity, to_entity, relation_type(属于/触发/产生/依赖...), source_doc
@dataclass
class Rule:     id, condition, conclusion, source_doc, confidence   # 业务规则（含合规红线）

class OntologyStore:
    def upsert_batch(self, project_id, entities, relations, rules) -> MergeReport
        # 增量 merge：同名实体属性合并，重复关系去重——新文档只增不重建
    def get_graph(self, project_id) -> dict            # 节点+边（Dashboard Mermaid 直染）
    def find_entities(self, project_id, keyword) -> list[Entity]
    def business_model_summary(self, project_id) -> str # 本体图压缩摘要（注入 research prompt）
```

**抽取管线**（`src/ontology/extractor.py`）：LLM 结构化抽取（复用已验证的 JSON 能力 + required_keys 校验重试），Prompt 输出实体/关系/规则三列表；**Mock 模式**返回行业模板派生的示例本体（流程可跑通）。触发方式：`POST /ontology/extract`（任务化）或 research 前自动增量。

### 3.3 整合机制（卖点 1×2 枢纽）

| # | 机制 | 实现 | 受益方 |
| --- | --- | --- | --- |
| 1 | 本体=知识库 schema 层 | KnowledgeHit 可带 `entity_refs`；检索支持 `entity_type` 过滤 | 检索精度↑ |
| 2 | **Research RAG 化** | `_perform_analysis` 输入改为：检索 top-k 相关块（带出处）+ `business_model_summary()`（本体压缩摘要）替代全文塞入 | 大文档稳定性↑ 成本↓ 出处可追溯 |
| 3 | **Benchmark 溯源** | 用例生成从 KB 检索，每条 `test_case.source = {filename, para}` | 验收标准可追溯（合同级） |
| 4 | **迭代闭环回写** | `_suggest_fix` 的 knowledge/rule 类型 → 生成 `CuratedEntry` 草稿 → 审核通过 `add_curated` → 下轮回归命中 | 知识飞轮真实转动 |

### 3.4 API 设计

```
知识库（卖点2）                          本体（卖点1）
GET  /projects/{id}/kb/stats             GET   /projects/{id}/ontology
POST /projects/{id}/kb/ingest（重建）     POST  /projects/{id}/ontology/extract（任务化增量抽取）
GET  /projects/{id}/kb/search?q=&k=      GET   /projects/{id}/ontology/graph.mermaid
GET  /kb/entries?status=pending          GET   /projects/{id}/ontology/entities?q=
POST /kb/entries/{id}/confirm            （Dashboard：本体图视图 + 知识条目审核队列）
```

## 四、实施计划（v0.4.0 三步走，每步独立可发布）

| 步 | 内容 | 验收 |
| --- | --- | --- |
| **a. 知识库独立化**（卖点2主体） | `src/knowledge/` 包 + LocalFts 默认后端 + 上传自动 ingest + kb API + Benchmark 溯源 | 零依赖：上传 10 文档→自动建库→检索有结果→Benchmark 用例带 source |

| **c. 整合与回归** | Research RAG 化 + 本体注入 + 迭代闭环 CuratedEntry + **黄金集 20 条回归** | 黄金集命中 ≥100%（不倒退）；RAG 模式下单条 token 成本下降（记录对比数据） |

每步完成后跑全量测试 + 黄金集抽查；v0.4.0 发布时更新 golden-real 报告（MiniMax 真实数据，RAG vs 全文对比两栏）。

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| FTS trigram 中文检索质量不达预期 | ① 黄金集回归兜底 ② 词级切块增强（标题+段落双索引）③ 文档如实标注"基础检索"，向量模式一键升级 |
| RAG 化后黄金集倒退 | 分步灰度：先"RAG+全文摘要"混合，回归通过再纯 RAG；倒退则保留全文模式为默认 |
| 本体抽取质量（LLM 幻觉实体） | required_keys 校验 + 每实体带 source_doc 溯源 + Dashboard 人工删除接口 + 抽取置信度标注 |
| 迭代闭环误写知识库 | CuratedEntry 必须"人工确认"才入库（与审核工作台同机制），AI 只产草稿 |
