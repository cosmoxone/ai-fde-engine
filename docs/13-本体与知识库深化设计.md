# 卖点 1+2 深化设计：本体抽取 × 知识库独立模块

> 版本：设计稿 **v1.1**（2026-09-14 修订，2026-09-17 契约摘要对齐）｜ 目标版本：v0.4.0 ｜ 状态：架构已对齐
> **2026-09-17 微调**：§3.1 契约摘要与 [14-知识库接口规格](14-知识库接口规格.md) **v1.1** 对齐（curate 提交即 `pending`；stats 移除 `coverage`、新增 `pending_parse`）。**14 号为唯一权威契约源，本节仅为摘要，冲突时以 14 为准。**
> **v1.1 修订要点（架构对齐）**：知识库为**独立模块接入**（可独立部署），本项目定位为——
> ①用户界面（Dashboard/API/审核工作台）②前期处理（解析/切块/元数据预加工）③交互处理（人工确认/编辑）④编排消费（research/benchmark 检索）。
> 本项目不内嵌知识库后端；提供**契约 + 内置参考实现**（开发/演示/单机零依赖）。
> 原则：契约先行、单机零依赖可跑（参考实现兜底）、验证前置（黄金集不倒退）、Mock-first

## 一、现状与差距（对照代码实况）

### 卖点 1：本体抽取与需求分析

| 环节 | 现状（v0.3.0） | 卖点主张 | 差距 |
| --- | --- | --- | --- |
| 文档输入 | DocParser 解析为纯文本 + structured 段落 | 客户数据 + **主动调研** | 主动调研缺位 |
| 抽取 | research 时 LLM 一次性输出 JSON（business_process 文本列表） | **本体抽取**（实体/关系/规则的结构化沉淀） | 输出是"描述文本"不是"可查询本体"，不可复用 |
| 建模 | requirements_baseline 里的业务流程为一次性生成 | 业务建模（本体图驱动） | 无图结构、无增量、每次全量重跑 |
| 需求分析 | 全部文档塞 prompt（M2.7 实测 100% 要点命中，单文档场景优秀） | 大文档量也稳定 | **文档多时超 context / 成本爆炸**，无检索增强 |

### 卖点 2：自动知识库 + 自动化 Benchmark

| 环节 | 现状 | 卖点主张 | 差距 |
| --- | --- | --- | --- |
| 知识库 | `tools/knowledge_base.py` 存在但**不在主流程**（孤岛：无任何端点触发建库） | 自动搭建知识库 | 文档上传后不会自动入库 |
| 后端 | qdrant 或 mock 二选一 | 开箱即用 | 缺**零依赖本地后端**（SQLite FTS5 即可，中文 trigram 分词可用） |
| Benchmark | 直接从文档原文生成 | 自动化 Benchmark | 不经知识库检索，**用例无出处溯源** |
| 迭代闭环 | badcase 修复建议是文本草稿 | 闭环沉淀 | "知识缺失"类 badcase 未回写知识库（建议→确认→入库缺失） |

**结论：两个卖点的核心差距交汇于同一缺失——「知识库独立模块」既没建成，也没把卖点 1/2 串起来。**

## 二、目标架构（v1.1：模块分离）

### 2.1 职责分离

```
┌─ ai-fde-engine（编排层 + 界面 + 预处理 + 交互）────────────┐
│  客户文档（上传/API/批量）                                   │
│       ▼                                                     │
│  【前期处理管线】解析(DocParser) → 切块(段落/标题感知)        │
│       → 元数据预加工(可选实体预标注) → ingest 推送 ──────────┼──►
│                                                             │     ▼
│  【交互处理】待确认队列(pending) ◄──────────────────────────┼── 知识库独立模块
│       → Dashboard 审核确认/编辑 → curate 写回 ─────────────┼─► (可独立部署)
│                                                             │     │
│  【编排消费】research(RAG检索) / benchmark(带溯源生成)       │     │
│       ◄──────────── search / pending ──────────────────────┼─────┘
│                                                             │
│  本体抽取（卖点1）：OntologyStore 留在本项目（业务建模层，   │
│  与交互强耦合）；抽取结果可作为知识库 schema 同步（可选）    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 接入模式（两档）

| 模式 | 配置 | 说明 |
| --- | --- | --- |
| **A. 独立部署**（生产形态） | `KNOWLEDGE_SERVICE_URL=http://kb:9000` | 知识库独立进程/独立仓库部署，HTTP 契约对接 |
| **B. 内嵌参考实现**（默认，零依赖） | 未配置 URL | 本项目内置**契约参考实现**（SQLite FTS5），同进程运行——开箱即用，亦是契约的行为参照与单测基准 |

### 2.3 关键设计决策

1. **契约先行**：本项目定义知识库接口契约（HTTP，见 §3.1），任何实现该契约的服务均可接入（换 Qdrant 版/云服务版/自研版不动本项目代码）
2. **参考实现即规格**：内置 SQLite FTS5 参考实现保证契约可执行、单机可跑、测试可断言；第三方实现以它为行为基准
3. **本体留本项目**：本体是业务建模层（与需求分析/人工编辑强耦合），放 `src/ontology/`；其抽取结果**可选同步**给知识库作 schema 过滤维度（不强制耦合）
4. **Embedding 归知识库**：向量/索引技术选型是知识库模块的内政；本项目只传文本块与元数据

## 三、模块设计

### 3.1 知识库契约与接入层（`src/knowledge/`）

**HTTP 契约**（独立知识库模块需实现；亦是本项目参考实现的规格）：

```
POST /ingest          {documents:[{title, content, metadata:{doc_id, title_path, entity_hints}}]}
                      → {accepted, deduped}          # 文档级主协议（决策1）；幂等按 doc_id；最终一致
POST /ingest/chunks   {chunks:[…]}                    # 降级模式（14 附录A）：损失 Summary/Wiki/语义切块
POST /search          {query, top_k, filter:{entry_type?}}
                      → {hits:[{content, source:{filename, chunk_index, start_at, end_at, knowledge_id}, score, entry_type}]}
POST /curate          {entry:{question_pattern, answer, origin?, similar_questions?}}
                      → {entry_id, status: pending}  # 提交即 pending；幂等 origin+question_pattern
GET  /pending         ?page=&page_size=   → {total, page, page_size, entries:[…]}   # 页码分页
POST /entries/{id}/confirm | /reject    （交互处理写回；幂等，终态不可逆）
GET  /stats           → {documents, parsing, curated, pending, (chunks, parse_failed, rejected)}
```
> 请求体不带 `project_id`（scoped key 即项目身份，决策2）；就绪判据 `parsing == 0`；三元不变量
> `documents + parsing + parse_failed = 累计已接受`。端点能力域、错误码表（含 kb-os 映射）详见 14 号 §2/§4；本摘要如与 14 号冲突，以 14 号为准。

**本项目侧代码结构**：

```python
# src/knowledge/gateway.py
class KnowledgeGateway(ABC):
    """知识库接入抽象：契约的客户端形态"""
    def ingest(self, project_id, chunks) -> IngestReport
    def search(self, project_id, query, top_k=5, **filters) -> list[KnowledgeHit]
    def submit_curated_draft(self, project_id, entry) -> str      # 提交草稿（进 pending）
    def list_pending(self, project_id) -> list[PendingEntry]      # 拉取待确认（Dashboard 审核队列）
    def confirm_entry(self, entry_id, action, edited=None)        # 交互处理写回
    def stats(self, project_id) -> dict

class RemoteKnowledgeGateway(KnowledgeGateway):   # 模式A：HTTP 客户端
    """KNOWLEDGE_SERVICE_URL 配置即启用；超时/重试/降级策略"""

class EmbeddedKnowledgeGateway(KnowledgeGateway): # 模式B：内置参考实现（默认）
    """SQLite FTS5(trigram) + kb_curated 表；契约行为基准"""

def get_knowledge_gateway() -> KnowledgeGateway   # 工厂：按配置选择
```

**数据落点（参考实现）**：`data/aifde.db` 增 `kb_chunks`(FTS5 虚表) 与 `kb_curated` 表；独立部署时数据归知识库模块自管。

**前期处理管线**（`src/knowledge/preprocess.py`，本项目职责②）：
- `chunk_document(doc: dict) -> list[chunk]`：段落/标题感知切块（300-500 字），保留结构元数据
- `pre_annotate(chunks) -> chunks`：可选实体预标注（为 schema 过滤预置 metadata，v0.4-b 后增强）
- 上传/批量导入后自动触发 `ingest`（失败不阻断，报告状态进文档记录）
- **v1.2 起 ingest 为文档级**（切块主权归知识库侧，联合方案决策1）：主流程推整篇文档+元数据预标注；`chunk_document` 切块器保留，供 **Embedded 参考实现内部**与附录 A 降级模式使用

### 3.2 OntologyStore（卖点 1 主体，`src/ontology/`）

```python
# src/ontology/store.py
@dataclass
class Entity:   id, type(物料/检验单/角色/系统/流程节点...), name, properties: dict, source_doc
@dataclass
class Relation: from_entity, to_entity, relation_type(属于/触发/产生/依赖...), source_doc
@dataclass
class Rule:     id, condition, conclusion, source_doc, confidence   # 业务规则（含合规红线）

class OntologyStore:
    def upsert_batch(self, project_id, entities, relations, rules) -> MergeReport
        # 增量 merge：同名实体属性合并，重复关系去重——新文档只增不重建
    def get_graph(self, project_id) -> dict            # 节点+边（Dashboard Mermaid 直染）
    def find_entities(self, project_id, keyword) -> list[Entity]
    def business_model_summary(self, project_id) -> str # 本体图压缩摘要（注入 research prompt）
```

**抽取管线**（`src/ontology/extractor.py`）：LLM 结构化抽取（复用已验证的 JSON 能力 + required_keys 校验重试），Prompt 输出实体/关系/规则三列表；**Mock 模式**返回行业模板派生的示例本体（流程可跑通）。触发方式：`POST /ontology/extract`（任务化）或 research 前自动增量。

> **✅ 实现状态（v0.4-b，2026-09-17）**：`src/ontology/` 七模块已交付（types/store/extractor/gateway/service/server/__init__）；
> 对外独立服务契约见 [20-本体服务接口规格](20-本体服务接口规格.md) v0.1-draft（Embedded/Remote/Fallback 三态同构，
> 镜像知识库接入层）；`entity_hints` 预标注已回填 `knowledge/pipeline.doc_record_to_spec`（本体不可用回退空，不违契约 14 号"存而不滤"）。

### 3.3 整合机制（卖点 1×2 枢纽）

| # | 机制 | 实现 | 受益方 |
| --- | --- | --- | --- |
| 1 | 本体=知识库 schema 层 | KnowledgeHit 可带 `entity_refs`；检索支持 `entity_type` 过滤 | 检索精度↑ |
| 2 | **Research RAG 化** | `_perform_analysis` 输入改为：检索 top-k 相关块（带出处）+ `business_model_summary()`（本体压缩摘要）替代全文塞入（决策依据与 RAG-less 辨析见 [18 号](18-RAG化技术立场-v0.4-c决策依据.md)） | 大文档稳定性↑ 成本↓ 出处可追溯 |
| 3 | **Benchmark 溯源** | 用例生成从 KB 检索，每条 `test_case.source = {filename, para}` | 验收标准可追溯（合同级） |
| 4 | **迭代闭环回写** | `_suggest_fix` 的 knowledge/rule 类型 → 生成 `CuratedEntry` 草稿 → 审核通过 `add_curated` → 下轮回归命中 | 知识飞轮真实转动 |

## 四、实施计划（v0.4.0 三步走，每步独立可发布）

| 步 | 内容 | 验收 |
| --- | --- | --- |
| **a. 契约与接入层**（卖点2） | `src/knowledge/`：HTTP 契约定稿 + `KnowledgeGateway` 抽象 + `EmbeddedKnowledgeGateway` 参考实现（SQLite FTS5）+ `RemoteKnowledgeGateway`（HTTP 客户端）+ 前期处理管线（切块/自动 ingest）+ Dashboard 待确认队列（交互处理） | ① 零依赖：上传文档→自动 ingest→检索有结果 ② 契约测试双实现通过（Embedded 直跑 + Remote 起参考服务对接）③ pending→confirm 闭环可操作 |
| **b. 本体抽取**（卖点1主体） | `src/ontology/` + LLM 抽取管线（增量 merge）+ 本体 API + Dashboard Mermaid 图 | 多文档项目实体≥20/关系≥15；图可渲染；重复抽取不重复计数 |
| **c. 整合与回归** | Research RAG 化（经 Gateway 检索）+ 本体注入 + 迭代闭环 CuratedEntry + **黄金集 20 条回归** | 黄金集命中 ≥100%（不倒退）；RAG 模式下单条 token 成本下降（记录对比数据） |

每步完成后跑全量测试 + 黄金集抽查；v0.4.0 发布时更新 golden-real 报告（MiniMax 真实数据，RAG vs 全文对比两栏）。

## 五、风险与对策

| 风险 | 对策 |
| --- | --- |
| FTS trigram 中文检索质量不达预期 | ① 黄金集回归兜底 ② 词级切块增强（标题+段落双索引）③ 文档如实标注"基础检索"，向量模式一键升级 |
| RAG 化后黄金集倒退 | 分步灰度：先"RAG+全文摘要"混合，回归通过再纯 RAG；倒退则保留全文模式为默认 |
| 本体抽取质量（LLM 幻觉实体） | required_keys 校验 + 每实体带 source_doc 溯源 + Dashboard 人工删除接口 + 抽取置信度标注 |
| 迭代闭环误写知识库 | CuratedEntry 必须"人工确认"才入库（与审核工作台同机制），AI 只产草稿 |
